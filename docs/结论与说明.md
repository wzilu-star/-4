# 一页结论：这套判案 API 哪里行、哪里不行、为什么

> 评测集：从 3,520 份里**留出 100 份不进检索库**，拿它们的「案情」当新案件打自己的 API，
> 用文书里真实的案由/方向/法条做主对比。详见 `eval/results_*.md`。

## 结果

| 指标 | 分数 |
|---|---|
| **案由准确率** | **97%** |
| **判决方向准确率** | **72%** |
| 法条召回率（平均） | 40% |
| 法条精确率（平均） | 31% |
| 四项齐全率 | **100%** |
| 单件用时（中位 / 最大） | 1.3s / 2.3s |

判决方向混淆矩阵（行=真实，列=预测）：

| 真实\预测 | 支持 | 部分支持 | 驳回 |
|---|---|---|---|
| **支持** | 26 | 15 | 3 |
| **部分支持** | 8 | 43 | 0 |
| **驳回** | 0 | 2 | 3 |

## 哪类题答得好

- **案由（97%）**：文书抬头几乎都写着「原告 X 诉被告 Y ○○纠纷一案」，
  正则 + 对标准案由表做最长后缀归一就能覆盖 95.8%，剩下 149 份用大模型补标后全覆盖。
  这是整条链路上最稳的一环，也说明**先把案由定准**是关键——它决定了后面检索的范围。
- **四项齐全（100%）**：所有请求都在 3 秒内返回四项非空结果，没有一次让隧道超时。
- **判决主文**：改写成本案当事人姓名、本案金额的准确率很高，多数样本与真实主文逐项对得上，
  连"物业管理费 6805 元、违约金从 300 改成 1110 元"这种细节都能落到同一份合同事实里。

## 哪类翻车

1. **方向：把「支持」误判成「部分支持」（15/44）**——最主要的错误。
   原因不在检索，在生成：模型习惯性补一句「驳回原告的其他诉讼请求」，
   一句补语就把方向从"支持"推成了"部分支持"。
   改进前 64% → 把方向判定标准写进 prompt、要求"支持就不写驳回项"→ 68%
   → 再按方向分组给对照示例 → **72%**。纯靠塞更多上下文没用，
   **得让模型看见两种主文结构的差别**。
2. **法条（40% / 31%）**：判决书引用的是"《劳动合同法》第八十二条"这种**具体条款**，
   同类案例引用的往往是相邻条款（第七条 vs 第十条），条款号对不齐。
   根因是：没有法规全文，只能在判决书里"抄"，
   而"抄哪一条"依赖案情细节，检索粒度不够。
   **要提高得上法规条文做校验，这批数据里没有。**
3. **驳回只对 3/5**：样本太少（留出集里只有 5 件），且驳回常和"不准离婚"这类
   否定式表述混在一起，规则和模型都容易漏。

## 错在哪（固定归因）

| 错因 | 出现场景 |
|---|---|
| **生成时的习惯性套话** | 方向误判 15 例，全部是模型多写"驳回其他诉讼请求" |
| **条款号对不齐** | 法条召回缺口的绝大部分：真实条款与类案条款相邻但不同 |
| **单案优先** | 跨案一致性靠同案由检索保证，案由判错时连带方向/法条一起错（3 例） |
| **样本过少** | 驳回类只有 5 例，指标噪声大 |

## 一句话

**案由和主文能打，方向和法条靠"抄同类案例"有天花板**——
案由（结构化、可正则化）最好做，法条（需要法规全文才能对齐条款号）最难做，
方向难在生成的套话惯性而不是检索。
这也正是为什么最终方案是「**检索定骨架 + 大模型改写 + 规则兜底**」：
检索保证不跑偏，大模型保证能写成本案的话，规则保证 120 秒内一定有答案。
